# 按版本目标迭代工作流

## 1. 生命周期

```text
输入 → 分诊 → Backlog → 版本范围确认 → 开发/验证 → 发布候选 → 正式发布 → 复盘
```

1. **输入**：产品想法、用户反馈、客户问题报告、技术债或发布风险进入 Linear。
2. **分诊**：判断是 Feature、Improvement、Bug 还是无效/重复；客户自动报告先在控制面聚合，不能直接批量创建 Linear Issue。
3. **Backlog**：未承诺版本的 Issue 保持 `Backlog`。它必须具备问题背景、影响、验收标准和目标发布线。
4. **版本范围确认**：创建目标版本的 Milestone（或配置 Release Pipeline 后创建 Release），将已确认的 Issue 移入 `Todo` 并关联该版本。此时创建/更新本地版本需求文档。
5. **开发与验证**：Issue 依次进入 `In Progress`、`In Review`、`Done`。每个实现提交和 PR 应引用 Linear Issue 标识；验证结果回写 Issue。
6. **发布候选**：冻结范围，只允许明确的 release-blocking Bug 进入。记录最终分支、提交 SHA、构建运行、测试、平台验收和已知风险。
7. **正式发布**：创建规范 Git tag，保存构建物、SHA-256、签名/公证证据与部署记录；将对应 Linear Milestone/Release 标为完成。
8. **复盘**：将遗漏项、客户问题和后续优化新增为 Backlog，不修改已发布版本的范围事实。

## 2. 版本目标的最小准入条件

一个版本在 Linear 中可从 Backlog 进入执行阶段前，必须明确：

- 发布线和版本号，例如 `Desktop v1.0.7`。
- 用户价值、范围和非目标。
- 关联 Issue 清单与每项验收标准。
- 目标分支、预期 Git tag、目标平台/部署环境。
- 发布门禁、已知依赖和回滚方式。

未满足这些条件的需求只能停留在 Backlog，不得因为“已经开始写代码”而默认进入下个版本。

## 3. 单人阶段的责任分工

当前负责人可在一个迭代中兼任以下角色，但每一步仍需留下可审计记录：

| 角色 | 最低产出 |
| --- | --- |
| 产品负责人 | 版本目标、优先级、范围与非目标 |
| 技术负责人 | 技术方案、分支、依赖、迁移与回滚判断 |
| 开发 | 关联 Issue 的提交、测试和实现说明 |
| 测试/验收 | 自动化结果、实机/环境结果、未覆盖风险 |
| 发布负责人 | tag、构建物、校验和、签名、部署与发布结论 |
| 分诊负责人 | 客户报告去重、关联 Bug/Feature、关闭结论 |

后续引入 AI 或人工角色时，按上述产出交接；AI 可以辅助总结、生成测试建议和维护文档，但版本准入、发布与客户数据分诊仍须由负责人确认。

## 4. Definition of Ready / Done

**Ready**：Issue 已有类型、优先级、目标发布线、验收标准、依赖和必要的需求文档链接。

**Done**：代码已合并到目标发布分支，自动化验证通过，必要的实机/部署验收已记录，文档和 Linear 状态已回写。对于正式发布，`Done` 还必须包含构建物和版本证据；仅完成代码不能称为“已发布”。
