# Electron 自动/手动更新需求变更单

| 项目 | 内容 |
| --- | --- |
| 变更编号 | `CM-CR-20260725-001` |
| 日期 | 2026-07-25 |
| 状态 | 已审核，可进入技术设计 |
| 影响范围 | macOS x64、macOS arm64、Windows x64 桌面客户端 |
| 目标版本 | 下一个桌面安装包版本 |
| 关联问题 | 频繁修复后需要客户重新下载安装包，交付链路长、验证成本高 |

## 1. 变更背景

当前桌面端所有修复都随 Electron 安装包发布。Windows 启动、托盘、远程通道、会话展示等问题一旦修复，客户仍必须重新下载并安装完整包才能生效。

该流程存在三个问题：

- 客户侧操作成本高，尤其是 Windows 环境需要多次远程协助。
- 修复发布到客户生效之间存在明显延迟。
- 同名版本重打包容易造成包哈希、客户实际安装版本和代码提交不一致。

本次变更只引入 Electron 应用更新能力，不做自研 JS 热更新、不做 Codex CLI 自动升级、不做 cloudflared 独立升级。

## 2. 目标

- 客户首次安装包含更新能力的版本后，后续版本升级不再要求客户手动访问下载页重新下载安装包。
- 支持自动更新：应用启动后自动检查新版本，后台下载，下载完成后提示用户重启安装或在退出时安装。
- 支持手动更新：用户点击“检查更新/立即更新”后，立即检查、下载并安装新版本。
- Windows 和 macOS 行为一致，差异仅体现在系统安装机制和签名要求上。
- 更新过程不丢失用户数据、设备绑定、本地访问密码、诊断日志和 Codex 会话。

## 3. 非目标

- 不实现绕过下载的“无字节传输更新”。Electron 更新本质仍需要下载新安装包或差分包，只是对用户无感。
- 不实现 Codex CLI 自动安装或自动升级。
- 不实现 cloudflared 单独在线升级；cloudflared 仍随 Electron 包更新。
- 不实现任意远程代码热更新，避免绕过签名、审核和回滚流程。
- 不支持从较新版本自动降级到较旧版本。

## 4. 用户场景

### 4.1 自动更新

1. 用户启动 Codex Manage。
2. 应用在后台检查更新，不阻塞本地服务、Tunnel 和会话列表。
3. 如果没有新版本，应用不打扰用户，只记录诊断日志。
4. 如果存在新版本，应用后台下载更新包。
5. 下载完成后，应用展示“新版本已就绪，可重启安装”。
6. 用户选择立即重启时，应用停止本地服务和 cloudflared，执行安装并重启。
7. 用户不处理时，应用在下次退出时安装，或下次启动继续提示。

### 4.2 手动更新

1. 用户在设置页或托盘菜单点击“检查更新”。
2. 应用立即请求更新源。
3. 如果存在新版本，按钮切换为“立即更新”，并展示版本号、大小和主要变更。
4. 用户点击“立即更新”后，应用立即下载更新包。
5. 下载完成后，应用立即进入安装流程。
6. 安装前如果存在运行中的任务、等待审批、正在启动的 Tunnel 或未完成的诊断导出，必须提示风险并要求确认。
7. 用户确认后，应用停止 Tunnel、本地服务和子进程，调用 Electron 安装更新能力并重启。

### 4.3 更新失败

1. 网络不可达、更新源不可达、签名校验失败、哈希不匹配或安装失败时，应用显示明确错误。
2. 失败不得破坏当前已安装版本。
3. 用户可以继续使用旧版本，并可稍后重试。
4. 诊断日志记录脱敏错误码、版本号、更新源和阶段。

## 5. 功能需求

### 5.1 更新检查

- 应用启动完成后自动检查一次更新。
- 应用运行期间按固定周期检查更新，默认间隔建议为 6 小时。
- 用户可在设置页手动触发检查。
- 用户可在托盘菜单手动触发检查。
- 检查更新不得影响本地服务启动、Codex app-server 启动和 Tunnel 启动。

### 5.2 更新下载

- 自动更新发现新版本后允许后台下载。
- 手动更新必须立即下载，不等待下一次自动周期。
- 下载过程中展示进度、速度和剩余大小。
- 下载失败允许重试，不能无限高频重试。
- Windows 优先使用 NSIS 差分更新能力，减少下载体积。

### 5.3 更新安装

- 自动更新下载完成后默认不强制中断用户当前工作。
- 手动更新下载完成后进入立即安装流程。
- 安装前必须停止桌面端管理的本地服务和 cloudflared 子进程。
- 安装后应用应自动重启并恢复正常启动流程。
- 安装升级不得删除 `app.getPath("userData")` 下的账号缓存、设备凭证、日志和本地安全配置。
- 升级不得删除 `~/.codex/sessions`、Codex CLI 或用户项目文件。

### 5.4 版本与渠道

- 版本号必须使用递增 SemVer，禁止同一版本号重复发布不同内容给客户。
- 默认只启用 `stable` 渠道。
- 后续如需灰度，可通过 `stagingPercentage` 或独立更新路径实现。
- 客户端必须展示当前版本和可更新版本。
- 更新源必须能区分 macOS x64、macOS arm64 和 Windows x64。

### 5.5 更新源与发布产物

- 更新源必须使用 HTTPS。
- 推荐路径为 `https://codex.xmwefun.cn/updates/stable/` 或等效自有 CDN。
- Windows 发布产物至少包含 NSIS 安装包、`latest.yml` 和 `.blockmap`。
- macOS 发布产物至少包含 DMG、ZIP、`latest-mac.yml` 和 `.blockmap`。
- CI 构建完成后必须上传安装包、更新元数据和校验文件到同一发布源。
- 发布源不可由客户端用户配置，避免被替换为恶意更新源。

### 5.6 安全要求

- 正式自动更新包必须完成 macOS Developer ID 签名和 notarization。
- 正式 Windows 更新包必须完成 Authenticode 签名。
- 客户端必须依赖 Electron 更新器的签名和哈希校验。
- 更新日志不得记录用户密码、设备密钥、Tunnel Token、扫码授权码、Codex 对话和命令内容。
- 更新失败时不得自动降级或执行未签名包。

### 5.7 UI 要求

- 设置页展示当前版本、更新状态、上次检查时间和“检查更新”按钮。
- 托盘菜单增加“检查更新”或“立即更新”入口。
- 更新可用时展示版本号、发布时间和变更摘要。
- 下载中展示进度。
- 下载完成后展示“重启安装”和“稍后”。
- 手动更新路径中，“立即更新”必须执行下载并安装，不只打开下载页面。

### 5.8 诊断与运维

- 诊断日志记录更新阶段：`checking`、`available`、`not_available`、`downloading`、`downloaded`、`installing`、`error`。
- 诊断日志记录当前版本、目标版本、渠道、平台、架构和脱敏错误。
- 管理后台或下载页应能展示当前推荐版本、发布时间和 SHA-256。
- 发现严重问题时，运维可以撤回更新源中的 `latest*.yml`，阻止更多客户端获取该版本。

## 6. 状态机

```text
idle
  -> checking
  -> not_available
  -> available
  -> downloading
  -> downloaded
  -> installing
  -> idle
  -> error
```

要求：

- 任一阶段失败进入 `error`，但不得影响当前已安装版本继续运行。
- 手动更新从 `available` 或 `not_available` 状态触发时，必须重新检查远端版本，避免使用过期缓存。
- `installing` 前必须确认是否允许中断当前桌面运行态。

## 7. 审核结论

本变更可执行，但必须接受以下边界：

1. 现有客户仍需最后一次手动安装“包含更新器”的版本；从该版本之后才具备无手动下载升级能力。
2. 自动更新不是无下载，而是应用后台下载并安装，客户不再人工访问下载页。
3. macOS 自动更新需要 ZIP 更新产物，不能只发布 DMG。
4. 正式发布必须签名；未签名测试包只允许内部验收，不应给客户自动更新。
5. 同一版本号不得重打不同内容，否则自动更新、哈希校验和客户排障都会混乱。

审核结论：需求范围清晰，建议进入技术设计与实现。

## 8. 验收标准

1. 从旧版本启动后能自动发现更新并后台下载。
2. 用户点击“检查更新”能立即获取远端最新版本。
3. 用户点击“立即更新”能立即下载并进入安装，不跳转浏览器下载页。
4. Windows x64 能通过 NSIS 更新到新版本，更新后应用版本号变化。
5. macOS x64 和 arm64 能通过对应架构更新到新版本，更新后应用版本号变化。
6. 更新后账号登录态、设备绑定、本地密码、Tunnel 配置和诊断日志仍存在。
7. 更新过程中本地服务和 cloudflared 不遗留孤儿进程。
8. 签名或哈希校验失败时拒绝安装，并保留旧版本可用。
9. 网络失败后可重试，诊断日志能定位失败阶段。
10. 自动更新和手动更新均通过至少一轮真实安装包升级验证。
