# 套餐与订阅支付模块变更需求

## 1. 变更状态

- 状态：首版已实现，待微信/支付宝商户参数联调和生产价格配置。
- 日期：2026-07-29
- 范围：桌面端“套餐与订阅”、云端控制服务、管理员后台、数据库与审计。
- 目标：在现有套餐、订阅、权益、订单和支付预留模型基础上，接入真实支付能力。

## 2. 背景与现状

当前系统已经具备套餐、订阅、权益、订单和支付记录的数据结构，但真实支付链路尚未开放：

- 桌面端“套餐与订阅”展示当前套餐、权益和到期时间。
- “立即升级”按钮目前为禁用状态，仅提示支付即将开放。
- 云端控制服务已有订单、支付、退款和回调接口占位，但返回 `PAYMENT_NOT_AVAILABLE`。
- 管理后台可以查看订单、支付记录和订阅，并支持人工开通正式权益。
- 人工开通不会伪造支付记录，支付记录只应来自真实支付链路。

本次变更要求将“支付预留”升级为“真实支付可用”，并保持老客户端与已有人工权益兼容。

## 3. 已确认产品决策

### 3.1 支付渠道

首版同时接入：

- 微信支付。
- 支付宝。

后端必须保留支付渠道适配层，避免业务代码直接绑定某一个支付平台。

### 3.2 退款

首版不做自动退款闭环。

必须预留后台退款入口和数据字段，但默认不允许系统自动发起退款。退款操作可以先展示为“预留能力”或记录人工处理状态，后续再接入真实原路退款。

### 3.3 套餐与价格

套餐价格和周期由后台配置。

首版不应把价格、周期、套餐编码写死在桌面端。桌面端只能展示后端返回的可购买套餐。

### 3.4 支付后的订阅处理

- 免费用户支付正式套餐后：立即覆盖为正式套餐。
- 已有正式套餐用户继续购买正式套餐后：按当前有效到期时间顺延。
- 如果正式套餐已过期：从支付成功时间重新开始计算。
- 如果用户存在人工开通的正式权益：同样按有效到期时间顺延，不能覆盖导致权益缩短。

### 3.5 发票和对公转账

首版不做发票入口，不做对公转账入口。

## 4. 目标用户流程

### 4.1 桌面端购买流程

1. 用户进入“套餐与订阅”。
2. 客户端请求可购买套餐列表。
3. 用户选择套餐周期和支付方式。
4. 客户端创建订单。
5. 客户端弹窗展示支付二维码、金额、套餐、倒计时和订单状态。
6. 用户扫码支付。
7. 后端收到支付平台异步回调并验签。
8. 后端确认金额、币种、订单号和交易号。
9. 后端将订单标记为已支付。
10. 后端创建或顺延订阅，并发放权益。
11. 客户端轮询到支付成功后刷新当前订阅和权益。
12. 客户端关闭支付弹窗，并提示升级成功。

### 4.2 订单超时流程

1. 待支付订单创建后必须有支付有效期。
2. 支付二维码过期后客户端停止轮询。
3. 后端可通过定时任务或查询时懒处理关闭过期订单。
4. 用户重新点击购买时创建新订单，不复用过期支付二维码。

### 4.3 支付失败流程

1. 支付平台明确返回失败时，支付记录标记为失败。
2. 订单仍可保持待支付或转为失败，具体按渠道结果判断。
3. 不创建订阅，不发放权益。
4. 客户端展示失败原因和重新支付入口。

### 4.4 已支付但客户端未刷新

支付结果以服务端回调为准。

如果客户端没有收到轮询成功结果，用户重新打开桌面端时，客户端通过当前订阅和权益接口自动获得最新状态。

## 5. 后端接口需求

### 5.1 套餐列表

`GET /v1/plans`

保持向下兼容，新增字段只能增量返回。

建议返回字段：

- `id`
- `code`
- `name`
- `description`
- `price_cents`
- `currency`
- `billing_period`
- `duration_days`
- `status`
- `purchase_enabled`
- `features`

### 5.2 创建订单

`POST /v1/orders`

认证：用户登录态。

入参：

- `planId` 或 `planCode`
- `channel`：`wechat` 或 `alipay`
- `clientType`：`desktop`
- `returnUrl`：可选

要求：

- 只允许购买 `status=active` 且 `purchase_enabled=true` 的套餐。
- 订单金额以服务端套餐配置为准，不能信任客户端传入金额。
- 同一用户同一套餐可以限制短时间只存在一个待支付订单，避免重复创建。
- 订单号必须全局唯一。
- 创建订单时状态为 `pending`。

返回：

- `order.id`
- `order.order_no`
- `order.status`
- `order.amount_cents`
- `order.currency`
- `order.expires_at`

### 5.3 获取支付参数

`POST /v1/orders/:orderId/pay`

认证：用户登录态，且订单必须属于当前用户。

入参：

- `channel`：`wechat` 或 `alipay`

返回：

- `payment.id`
- `payment.channel`
- `payment.status`
- `payment.qr_code_url` 或 `payment.payload`
- `payment.expires_at`
- `order.status`

要求：

- 只允许待支付订单发起支付。
- 支付金额必须与订单金额一致。
- 重复调用时，如果已有未过期支付参数，可以返回原支付参数或重新生成，策略必须明确并保持幂等。

### 5.4 查询订单

`GET /v1/orders`

认证：用户登录态。

返回当前用户订单列表。

`GET /v1/orders/:orderId`

认证：用户登录态，且订单必须属于当前用户。

返回订单、最近支付记录和当前订阅变更结果。

### 5.5 关闭订单

`POST /v1/orders/:orderId/close`

认证：用户登录态，且订单必须属于当前用户。

要求：

- 只允许关闭待支付或支付中订单。
- 已支付订单不能关闭。
- 关闭后不能继续支付。

### 5.6 支付回调

`POST /v1/payments/:provider/callback`

认证：支付平台签名，不使用用户登录态。

要求：

- 必须读取原始请求体用于验签。
- 必须校验支付平台签名、时间戳和 nonce。
- 必须校验订单号、金额、币种、支付状态和渠道交易号。
- 必须幂等处理重复回调。
- 必须在数据库事务中更新订单、支付、订阅和权益。
- 成功处理后按支付平台要求返回确认响应。

### 5.7 后台退款预留

`POST /v1/admin/orders/:orderId/refund`

认证：管理员，且需要写权限。

首版要求：

- 接口和页面预留。
- 默认不发起真实自动退款。
- 可以记录管理员退款意向、处理状态、原因和审计日志。
- 后续接入真实退款时，不改变订单和支付主流程接口。

## 6. 状态模型

### 6.1 订单状态

- `pending`：订单已创建，等待支付。
- `paying`：已生成支付参数，等待平台结果。
- `paid`：支付成功。
- `closed`：订单超时或用户关闭。
- `failed`：支付失败且不可继续支付。
- `refunding`：退款处理中，首版预留。
- `refunded`：已退款，首版预留。

### 6.2 支付状态

- `created`：支付记录已创建。
- `pending`：等待用户支付。
- `succeeded`：支付成功。
- `failed`：支付失败。
- `closed`：支付参数过期或关闭。
- `refund_pending`：退款处理中，首版预留。
- `refunded`：已退款，首版预留。

### 6.3 订阅状态

- `active`：有效。
- `expired`：已过期。
- `cancelled`：已取消。

### 6.4 订阅来源

- `manual`：管理员人工开通。
- `payment`：真实支付开通。
- `promotion`：活动赠送。

## 8. 权益发放规则

支付成功后必须调用统一订阅权益服务，不允许支付模块直接散落写权益。

### 8.1 免费用户升级

- 创建新的正式套餐订阅。
- `starts_at` 为支付成功时间。
- `expires_at` 按套餐 `duration_days` 计算。
- 发放套餐对应权益。

### 8.2 正式用户续费

- 如果当前正式订阅仍有效，从当前 `expires_at` 顺延。
- 如果当前正式订阅无固定到期时间，需按后台策略处理，默认不缩短现有长期权益。
- 如果当前正式订阅已过期，从支付成功时间重新开始计算。

### 8.3 多次支付幂等

同一笔订单只允许产生一次有效订阅变更。

重复回调、客户端重复轮询或重复点击，都不能重复发放权益。

## 9. 管理后台需求

### 9.1 套餐配置

后台需要支持：

- 创建套餐。
- 编辑套餐名称、描述、价格、币种、周期、有效天数。
- 上架和下架套餐。
- 配置权益键和值。
- 配置是否允许购买。

### 9.2 订单管理

后台需要展示：

- 订单号。
- 用户。
- 套餐。
- 金额。
- 支付渠道。
- 订单状态。
- 创建时间。
- 支付时间。
- 关闭时间。
- 关联支付记录。

### 9.3 支付记录

后台需要展示：

- 支付渠道。
- 支付状态。
- 支付平台交易号。
- 金额。
- 回调接收时间。
- 回调验签结果。
- 错误信息。

### 9.4 回调日志

后台需要查看回调处理结果，但必须对敏感字段脱敏。

### 9.5 退款预留

后台展示退款预留入口：

- 记录退款原因。
- 记录管理员。
- 记录处理状态。
- 写入审计日志。
- 不默认调用支付平台退款接口。

## 10. 桌面端需求

### 10.1 套餐与订阅展示

桌面端展示：

- 当前套餐。
- 当前权益。
- 到期时间。
- 可购买套餐。
- 套餐价格和周期。
- 订单状态。

### 10.2 支付弹窗

点击购买后展示支付弹窗：

- 套餐名称。
- 金额。
- 支付方式切换：微信、支付宝。
- 二维码。
- 二维码过期倒计时。
- 支付状态。
- 取消订单。
- 支付成功后自动关闭或提示。

### 10.3 支付状态刷新

客户端必须：

- 轮询订单状态。
- 支付成功后刷新订阅和权益。
- 支付失败或超时后提示重新支付。
- 重启后仍能通过后端状态恢复正确展示。

## 11. 安全要求

- 支付金额必须由服务端套餐配置生成。
- 支付回调必须验签。
- 支付回调必须使用原始请求体。
- 支付成功必须校验金额、币种、订单号和交易号。
- 支付成功事务必须幂等。
- 管理后台退款预留操作必须写审计日志。
- 回调日志和诊断日志必须脱敏，不能泄露支付密钥、用户 token 或完整个人敏感信息。
- 支付密钥只能通过服务端环境变量或密钥管理系统配置，不能进入前端包和仓库。

## 12. 配置要求

服务端需要新增配置项：

- 微信支付商户号。
- 微信支付 AppId。
- 微信支付证书或 API v3 Key。
- 微信支付回调地址。
- 支付宝 AppId。
- 支付宝应用私钥。
- 支付宝公钥。
- 支付宝回调地址。
- 支付回调公开域名。
- 支付订单默认过期时间。

要求：

- 测试环境和生产环境配置隔离。
- 缺少支付配置时，支付接口应返回明确业务错误，不能影响登录、设备、Tunnel 和订阅查询。

## 13. 向下兼容要求

- 现有老客户端继续可以调用套餐、当前订阅和当前权益接口。
- 现有接口字段不得删除或改名。
- 新增字段必须为可选或有默认值。
- 已有人工开通的正式权益继续有效。
- 支付上线后不影响后台人工开通能力。
- 老版本客户端如果没有支付 UI，仍能展示支付后已开通的正式权益。

## 14. 验收标准

### 14.1 基础验收

- 用户可以在桌面端看到后台配置的套餐价格和周期。
- 用户可以选择微信或支付宝创建订单。
- 用户可以看到支付二维码和倒计时。
- 支付成功后自动刷新为正式套餐。
- 免费用户支付后立即升级。
- 正式用户续费后到期时间顺延。
- 支付失败不会开通权益。
- 订单超时后不能继续支付。

### 14.2 后端验收

- 回调验签失败时拒绝处理。
- 金额不一致时拒绝开通权益。
- 重复回调不会重复开通。
- 支付成功事务中断时不会产生半开通状态。
- 缺少支付渠道配置时返回明确错误。

### 14.3 后台验收

- 管理员可以配置套餐价格和周期。
- 管理员可以查看订单和支付流水。
- 管理员可以查看支付回调日志。
- 管理员可以记录退款预留操作。
- 所有后台敏感操作写入审计日志。

### 14.4 兼容验收

- 老客户端仍可读取当前订阅和权益。
- 人工开通用户不受支付上线影响。
- 支付上线后现有免费用户默认状态不变。

## 15. 不在首版范围

## 17. 风险与处理

- 支付平台回调延迟：客户端以轮询和重新打开后的订阅查询兜底。
- 重复支付：通过待支付订单限制、订单状态和回调幂等控制。
- 套餐改价：订单保存金额快照，历史订单不受影响。
- 人工权益和支付权益冲突：统一订阅权益服务按“不缩短用户有效权益”原则处理。
- 支付配置错误：支付接口失败不能拖垮核心登录、设备和 Tunnel 服务。

## 18. 解耦与复用决策

支付模块需要按“通用支付能力”和“宿主业务履约”拆分，便于后续其他项目复用。

### 18.1 通用支付模块负责

- 订单创建。
- 支付状态机。
- 微信支付适配。
- 支付宝适配。
- 支付回调验签。
- 回调幂等。
- 支付流水。
- 回调日志。
- 订单关闭。
- 退款预留记录。

### 18.2 宿主项目负责

- 用户认证。
- 套餐目录。
- 支付成功后业务履约。
- 订阅和权益发放。
- 管理审计。
- 老客户端兼容。

Codex Manage 的 `tunnel.quick`、`tunnel.named`、`device.max_count`、Named Tunnel 开通和设备限制等业务能力不得写入通用支付模块。

### 18.3 推荐落地方式

首版在当前仓库中新增 `packages/payment-*` workspace 包，暂不发布 npm：

- `payment-core`：类型、状态机、错误码和端口。
- `payment-service`：订单、支付、回调、幂等编排。
- `payment-pg`：PostgreSQL Repository 和迁移。
- `payment-fastify`：Fastify 路由插件。
- `payment-provider-wechat`：微信支付适配。
- `payment-provider-alipay`：支付宝适配。

### 18.4 数据表命名

通用模块内部表使用 `billing_` 前缀，避免其他项目已有 `orders`、`payments`、`plans` 表冲突。

Codex Manage 可以继续对外保留现有接口路径，但内部实现应逐步迁移到通用支付模块。

## 20. 首版实现说明

本次实现已完成：

- 新增 `packages/payment-*` 通用支付模块。
- 新增 `billing_` 前缀数据表。
- 控制服务接入 `/v1/billing/*` 和兼容 `/v1/orders/*`、`/v1/payments/:provider/callback`。
- 微信支付和支付宝 Provider 已实现服务端下单、回调验签和回调解析。
- 桌面端已实现套餐购买弹窗、支付二维码、倒计时、订单轮询和支付成功后权益刷新。
- 管理后台已实现套餐配置、订单退款预留和支付回调日志查看。
- Codex Manage 业务履约通过 `PaymentFulfillmentPort` 实现，支付成功后按免费覆盖、正式顺延规则发放权益。

生产上线前必须完成：

- 在运营后台配置套餐价格、周期、权益和 `purchase_enabled`。
- 配置微信支付商户参数和 HTTPS 回调地址。
- 配置支付宝应用参数和 HTTPS 回调地址。
- 使用沙箱或小额真实订单验证下单、扫码、回调、幂等和权益开通。
- 确认服务器已执行最新数据库迁移。

开发和测试环境可以设置 `BILLING_OFFLINE_PAYMENTS=true` 和 `BILLING_OFFLINE_SECRET` 使用离线签名 Provider 验证完整支付链路；生产环境不得开启离线支付。
