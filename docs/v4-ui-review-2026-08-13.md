# V4 UI 设计审核与交付边界

- 审核日期：2026-08-13
- 审核对象：`Codex Manage - ChatGPT Mac Style` 中的 V1/V4 UI 资产、V4 视觉导出，以及当前 Web/H5 实现与 V4 交互要求的对应关系
- 审核方式：UI 高级工程师、高级全栈开发工程师、ChatGPT Mac 桌面应用深度体验用户三种角色的独立审核与交叉审计
- 审核结论性质：设计审核与实现差距记录，不等同于生产代码验收通过

## 1. 审核范围

本次审核覆盖：

1. Figma 中的 V1 正式 UI 根画板：登录、会话列表、会话详情、审批与权限、模型选择与 Retry、设置与诊断、移动端响应式。
2. Figma 中的 V4 正式 UI 根画板：Entry、Workspace、Interruption States、Settings、Mobile。
3. V4 导出中的单一会话工作区、历史与实时 Timeline、命令输出、文件变化、审批、失败 turn、Retry、模型选择、Drawer、Approval Sheet 与 Composer。
4. 当前客户端的会话详情、实时事件、审批、模型状态、Retry、Timeline 合并和移动端布局实现。
5. 当前服务端 RuntimeManager 的 turn、runtime 状态、审批和模型切换协调。
6. V4.1 过程板与过程导出，仅用于识别实现差距和清理边界，不作为正式产品 UI 资产保留。

本次审核明确区分：

- **设计完成**：Figma 画板和视觉参考已经表达出完整的目标状态、交互语义和验收要求。
- **代码完成**：生产代码已实现这些状态和交互，并通过对应的真实视口、事件时序、可访问性和回归验收。

不能把前者误读为后者。

## 2. 总体结论

### 2.1 V4 设计结论：方向通过，可作为 Codex 实现依据

V4 的设计方向基本通过审核。它已经形成了比早期版本更清晰的单一会话工作区模型：左侧持久会话列表、中部统一对话 Timeline、底部 Composer，以及按状态插入的审批、命令、文件变化、失败和 Retry 操作。

V4 画板同时覆盖 Desktop 与 Mobile，并且把 Mobile Conversation、Drawer、Approval Sheet 和 Composer 放在同一交互模型下表达。审批文案、失败 turn 保留、显式 Retry、新 attempt、模型选择和权限模式均有明确语义，适合交给 Codex 按契约实现。

### 2.2 当前生产实现结论：不能通过 V4 完成验收

当前生产代码仍不能宣称通过 V4 完成验收。审核发现的主要原因不是视觉方向缺失，而是目标设计中的状态和交互约束尚未全部落到生产实现：

- Mobile Approval 仍未成为实际的覆盖式 bottom sheet；
- Detail 页面缺少可正常使用的移动 Drawer 入口与完整覆盖层关系；
- Canonical Timeline 尚未完成滚动保护、用户上滚后的不夺回、未读实时活动提示和“跳到最新”；
- 历史失败 turn 刷新后不能稳定恢复唯一 RetryContext；多个失败 turn 之间也存在错绑风险；
- Approval、Runtime 和异步刷新之间存在乱序回滚可能；
- Modal、Drawer、Sheet 尚未完成焦点进入、焦点陷阱、焦点恢复和完整 scroll lock；
- V4 的深色视觉 token 与当前生产 CSS 仍有差异；
- 375×812、390×844、430×932 三种目标视口尚缺少完整、可复现的生产 E2E 证据；
- 动态 agent 输出和错误状态尚缺少清晰、一致的 `aria-live` 播报策略。

因此，本地正式记录应写为：**V4 UI 设计审核通过作为实现依据；当前实现审核不通过 V4 完成验收。**

## 3. 已确认的设计优点

### 3.1 工作区结构

- 单一会话工作区比路由式功能页面更接近 ChatGPT Mac 的连续工作流。
- 左侧会话列表、中部 Timeline、底部 Composer 的层级稳定，能够承载历史、实时输出和中断状态。
- Composer 被作为主要交互边缘处理，模型选择和发送动作的关系清楚。

### 3.2 状态表达

- `running`、`waiting_approval`、`failed` 等状态有明确视觉层级。
- 审批位于暂停 turn 内，不会被误认为普通 Banner。
- 失败 turn 保留，Retry 表达为新的 attempt，而不是覆盖原失败记录。
- `Allow once`、`Allow for this session`、`Deny`、`Cancel` 四类审批动作语义完整。
- Full Access 下出现意外审批时仍保留可操作的 Deny/Cancel，不把异常状态变成不可恢复的锁死页面。

### 3.3 移动端与无障碍

- Mobile Conversation、Drawer 和 Approval Sheet 具有一致的状态来源。
- 375×812、390×844、430×932 三个目标视口被明确列为验收范围。
- 安全区、键盘、触控区域、scrim、系统返回、对话框语义和焦点管理都有明确设计要求。
- 44px 最小触控目标、`role="dialog"`、`aria-modal`、`role="alert"`、焦点进入/恢复等要求具备可实现性。

## 4. P1 必须修复项

以下问题会直接影响 V4 核心交互的可用性、状态正确性或验收可信度：

1. **Mobile Approval bottom sheet 未落地**
   - 设计要求是覆盖式 bottom sheet，而不是 Timeline 中的静态三联页面。
   - Sheet 关闭不能清除 pending；审批提交中、失败、已解决、多 pending 和重新打开状态都需要可操作。

2. **Detail 页面 Mobile Drawer 不完整**
   - 需要真实入口、scrim、关闭按钮、系统 Back 关系、会话搜索和焦点恢复。
   - Drawer 打开时不能破坏当前会话、Composer 草稿或审批 pending 状态。

3. **Canonical Timeline 缺少滚动保护与跳到最新**
   - 用户上滚阅读历史时，新的 agent delta、命令输出或审批不能强制夺回滚动位置。
   - 需要检测是否接近底部、显示未读实时活动提示，并提供明确的“跳到最新”。
   - 历史、live、optimistic、approval、error 和 retry marker 必须保持稳定排序。

4. **Retry 缺少稳定的历史 turn 与唯一 attempt 绑定**
   - 刷新历史后必须能恢复失败 turn 的 RetryContext。
   - 不能用任意 terminal error 加任意 user message 猜测绑定。
   - 多个失败 turn、Retry 失败和新 attempt 必须互不覆盖；Retry 必须保留原失败记录并创建新 turn。

5. **Approval/Runtime 异步状态存在竞态**
   - `approval_requested`、`approval_resolved`、runtime snapshot 和异步 reload 可能乱序到达。
   - 旧响应不能回滚新 pending 状态，也不能让 Composer 在 waiting approval 时错误可用。
   - Full Access 下的 unexpected approval 仍必须保持 Deny/Cancel 可见。

6. **Modal、Drawer、Sheet 的焦点管理和 scroll lock 不完整**
   - 打开时需要焦点进入，交互期间需要焦点陷阱，关闭时恢复到触发控件。
   - 对话框打开时底层 Timeline 不能继续滚动或接受错误的键盘操作。
   - Escape 与移动端系统 Back 必须遵循 overlay 优先级。

7. **Runtime settings waiter timeout 必须清理**
   - `settingsWaiter` 超时后若只 resolve 而不从 map 清理，reload blocker 会长期存在。
   - 这可能使 `modelChangeStatus` 停在 `confirming`，并令 `/api/runtime/reload` 永久阻塞。
   - 这是服务端状态机的 P1 问题，不应被仅视为测试清理问题。

## 5. P2 建议项

1. **Approval reconciliation**：终态只由服务端权威响应确认；网络错误、超时和无响应不能伪造 `failed` 并移除 pending。
2. **Timeline identity/order**：在缺少 `itemId` 时使用 occurrence count、turn 关联、event sequence 和 `createdAt`，避免同一 turn 中相同文本的真实消息互相去重。
3. **视觉 token 收敛**：将 V4 的 canvas、sidebar、surface、border、文字、running、approval、failed token 与生产 CSS 统一。
4. **三视口 E2E**：对 375×812、390×844、430×932 分别验证 Drawer、Sheet、Composer、键盘、安全区和无横向溢出。
5. **动态输出播报**：明确 agent delta、命令输出、审批和 terminal error 的 `aria-live` 策略，避免播报过密或关键信息静默。
6. **错误与 Retry marker identity**：`willRetry`、terminal error、source turn 和新 attempt 应使用可追踪的稳定 key，避免刷新后出现重复或错配。
7. **提交失败后的局部刷新**：审批 POST 异常时要同时保留可重试提示并重新协调 pending approvals 与 runtime，而不是只 reload runtime。

## 8. Codex 实现责任边界

本文件只记录审核结果和实现边界，不宣称已经完成 P1/P2 修复。后续由 Codex 按 V4 设计和项目现有 API 能力实现：

- 先补齐状态契约和稳定 identity，再补 UI 覆盖层与 Timeline 行为；
- 不新增不存在的 Stop API 或 New chat API；
- 不自动 Retry、Replay、模型降级或在运行中切换模型；
- 以真实事件时序、三种移动视口和无障碍交互完成验收；
- 设计稿、截图和本审核文档不能替代生产代码测试。

## 9. 最终判断

**V4 Figma 设计与视觉资产可以作为 Codex 的实现依据；当前生产实现仍不能通过 V4 完成验收。**
