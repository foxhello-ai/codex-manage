# 外网加载与大数据量 UI 验收

日期：2026-11-03（Asia/Shanghai）。站点：https://codex.foxhello.cn 。本轮使用现有 357 个会话、4 个任务和现有成员进行了真实登录与只读交互检查；保留工作区已有未提交修改。

## 说明原因

1. 外网当时直连 4310 的 Vite 开发服务。HTML 中存在 `/@vite/client`、`/@react-refresh` 和 `/src/client/main.tsx`。仅实测的 App 模块与 React DOM 开发模块已约 1.79 MB，各自的公网请求耗时约 8.3、9.6 秒。
2. 列表首屏只展示 10 条，接口却顺序扫描最多 1,000 条原始记录；首页的任务查询同时再次扫描。357 条会话响应约 268 KB，公网单次请求约 9.2 秒。
3. 任务页在卡片下重复展开任务内会话，并展开 350 条未归类会话；工作目录的“展开更多”会一次展开全部。成员授权同样渲染全部会话。
4. 成员页实际复现 `app-server stopped`。随后查询 `/api/config` 显示 `runtimeReload.trigger=config_watcher`，运行时已恢复 ready：配置刷新会中断正在执行的只读查询。

## 当前代码问题点与修改方案

- 首屏改为读取上游 cursor 的一个 30 条原始记录页面，再去重；当前得到 26 个逻辑会话。页面先显示 10 条，分批显示并按需请求下一页。数量文案明确是“已载入”，不冒充全库总数。
- 任务页才查询任务；任务列表、详情、置顶和归入操作只读取被引用的会话，最多并发 4 个摘要读取，不再扫描无关历史。新建空任务不需要扫描；任务新会话仍使用既有上下文规则。
- 全量扫描共享正在执行的请求，并缓存原始记录 5 秒。每次重新应用最新备注和用户权限；成功写入后失效缓存，运行时进程变化后不复用缓存。失败不缓存。
- 列表专用摘要最多 240 字符，详细对话不裁剪。较大 HTTP 响应使用 gzip/deflate；React 运行时单独分包。
- 用户认证成功后立即显示工作台，不再等待诊断配置。刷新保留现有列表；新搜索取消旧请求并忽略过期响应。
- 任务卡片桌面双列；去掉重复任务会话列表，未归类默认收起，展开后分批显示。工作目录逐批显示；新建面板立即出现，后台补充历史目录。备注标题不再额外重复默认标题。
- 成员和可授权会话分别加载；授权列表支持搜索、每批 30 条，保留所有已选会话。统一受影响文案为中文，并提供错误重试入口。
- 仅对明确返回 `app-server stopped` / `Codex app-server is not ready` 的指定只读 API 自动重试一次。消息发送、会话创建、权限更新等写入不自动重放；其他 503 不重试。

## 实测数据

HTTP 单请求采样，不是整页 LCP，也不是多次平均值；公网网络本身存在波动。字节数是解压后的响应体大小。

| 项目 | 修改前 | 修改后 |
| --- | --- | --- |
| 公网首屏会话请求 | 9,165 ms / 267,911 B | 1,764 ms / 16,379 B，gzip |
| 公网任务请求 | 5,484 ms | 588 ms，gzip |
| App JS 公网请求 | 8,265 ms / 781,303 B，开发版 | 1,466 ms / 114,541 B，生产构建 |
| React JS 公网请求 | 9,575 ms / 1,005,207 B，开发版 | 1,574 ms / 191,817 B，生产构建 |
| 本机首屏会话请求 | 7,349 ms | 823 ms |
| 本机任务请求 | 基线一次 503，另见公网成功样本 | 56 ms，直接读取任务引用 |

原始记录：`baseline.json`、`after.json`、`final.json`。最后的请求重试和目录加载交互修正仅使 App 包增加约 1 KB；当前构建以工作区 `dist/client/index.html` 的资源哈希为准。

## 当前运行方式与剩余限制

当前 4310 已从 Vite 开发服务切换为构建后的前端，继续代理现有 4311 后端；外网隧道目标不变。后端仍是当前本地开发运行方式。此次没有发布 GitHub Release、提交或推送代码。

之后需要重新启动本地外网试用时，停止已有开发服务，再运行 `npm run local:public`。前端源代码变更后需要重新构建；正式部署继续使用单体生产运行包。已有 PWA 的缓存可能让第一次刷新先显示旧壳，浏览器验收已核对当前构建资源；必要时再次刷新。

完整工作目录/历史搜索目前仍沿用最多 1,000 条原始记录的兼容扫描，冷加载本机约 8 秒、公网样本约 13 秒。缓存和并发合并减少重复扫描，但没有消除第一次索引成本。下一步应为全量目录与历史搜索建立可增量更新的摘要索引；不能把首屏分页收益解释为所有历史查询都已同样加速。详情历史正文仍保留既有 API 和读取方式，超长历史的传输/解析成本尚需单独做后端分页。
