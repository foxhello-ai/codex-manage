04 / 官方桌面为什么仍不能跨端回答

当前结论：保持桌面版不修改，Web 不能直接处理其私有后台中的挂起交互。

已有文字队列可以发送后续聊天；审批或问答要求通过收到原请求的 JSON-RPC 连接答复。仅拿到 thread ID 或 request ID，不能替代这条连接。

  • 盘点版本：官方桌面 26.1002.52244，内置 CLI 0.162.0-alpha.2。
  • 170 个 client methods 中，未找到枚举或答复另一连接 pending 请求的接口。增减 elicitation 计数只用于超时记账，不传送问题或答案。
  • 当前默认后台没有外部 listener 参数和 TCP 监听；默认 daemon control socket 不存在。
  • 未修改桌面安装包、启动方式或真实会话，未绕过内部 app-tools 的授权与签名校验。
  • 共享 app-server 与启动适配器属于独立方案，需要改变启动链，不算本次“默认桌面不变”修复已完成。

这是当前安装版本的协议和入口盘点结论，不宣称所有内部接口或未来版本永远不可行。未创建并答复真实桌面挂起请求，用户所给截图的具体请求类型仍未知。

05 / 已登录 instabox，还能授权其他 GitHub 项目吗？

可以。无需取消旧项目，也无需重新登录 instabox。

目标项目怎么操作
同一个 GitHub 账号/组织的新仓库在该 OWNER 的 GitHub App 安装配置中扩大仓库范围，勾选新仓库并保留原仓库。
另一个 GitHub 账号或组织在 instabox 授权页选择 Install on another GitHub account，安装到目标 OWNER 并授予目标仓库访问，再将 OWNER Link 到当前 workspace。
提示 Already used for CI该 OWNER 已关联其他 workspace。确需迁移时，由管理员在原 workspace 解除关联，再关联到新 workspace；普通增加仓库无需做这一步。

限制是一个 GitHub OWNER 同时只能关联一个 instabox workspace，不是一个 workspace 只能有一个 GitHub OWNER。添加另一个 OWNER 可以保留现有授权。跨 GitHub 登录身份安装时，可能需要在 GitHub 切换到有权限的账号；不需要因此重新登录 instabox。

针对 foxhello-ai/codex-manage 的操作

  1. 打开 当前 workspace 的 GitHub 授权页。
  2. 如果列出 foxhello-ai，检查 App 是否已获 codex-manage 仓库权限，并确认已 Link 到当前 workspace。
  3. 如果未列出该组织，选择 Install on another GitHub account → foxhello-ai → 勾选 codex-manage，随后完成 Link。组织不可见或需审批时，由有相应组织权限的管理员完成。
  4. 本项目已完成 首次 Instabox Linux Pilot，GitHub 和 instabox ci 均成功。Linux 默认值已在实现分支切换，无需再设置启用变量；需要回退 GitHub runner 时可设置 LINUX_CI_RUNNER=ubuntu-24.04。

登录身份、GitHub App 的仓库授权范围、OWNER 与 workspace 的关联是三个独立步骤。安装与 Link 需要相应管理员操作，本报告未更改任何账号授权。

真实 CI 验收成功 · 无需补充授权

foxhello-ai/codex-manage 的 verify job 已由 instabox-medium 接受并成功完成；GitHub run 43148957035，job 130953338930。179 项测试、构建和安装验证均通过。任务由当前分支 push 触发，使用已有 git SSH 身份，未修改只读 gh 账号权限。

Linux 安装和发布默认 runner 的实现位于当前分支，合并 main 后生效；macOS runner 保留。原 fmzh2021 关联仍保留。

授权流程依据 instabox CI 文档及当前安装的 instabox 技能 CI 章节。OWNER 与 workspace 的关联规则来自技能；此次未更改已有授权；目标仓库访问通过真实任务核验。
